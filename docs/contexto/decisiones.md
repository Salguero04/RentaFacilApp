## SQL Server (local + producción) con schemas organizacionales
- **Decisión:** EF Core con SQL Server en todos los entornos. Las tablas se organizan en 4 schemas fijos (no por tenant): `auth` (identidad), `renta` (dominio, filtrado por `UsuarioId` por fila), `config` (catálogos globales + `__EFMigrationsHistory`) y `audit` (trazabilidad, hoy como columnas `IAuditable` en `renta.*`). Connection string por máquina vía user-secrets (`ConnectionStrings:Default`, `Integrated Security=true` en local). Migración única `InitialSqlServer`. Plan: `docs/superpowers/plans/2026-06-26-migracion-sqlserver.md`.
- **Por qué:** SQL Server ya está instalado en las máquinas de desarrollo (trabajo y casa); los schemas dan organización lógica y dejan lista la base para un futuro salto a BD-por-tenant (un `TenantDbContextFactory` que elija la connection string según el JWT — `IDbContextFactory` ya está registrado) sin tocar repositories/services/controllers.
- **Descartado:** **SQLite** (era la BD local de Fase 1, `Data Source=rentafacil.db`) y **MySQL** (era el destino de producción planeado) — ambos reemplazados por SQL Server el 2026-06-26. SQLite ignoraba `decimal(18,2)` y no soporta schemas reales; mantener dos providers (local vs prod) añadía fricción.
- **Estado:** vigente. Verificado end-to-end en la máquina de trabajo (`GGCBOADMWRK025\SQLEXPRESS`) y en la máquina de casa (2026-06-26, LocalDB instancia `MSSQLLocalDB`, connection string `Server=(localdb)\MSSQLLocalDB;...`): migración `InitialSqlServer` aplicada, los 4 schemas (`auth`/`config`/`renta`, `audit` aún como columnas en `renta.*`) y sus tablas creados, seed dummy + usuario admin insertados, API arrancando y escuchando en `0.0.0.0:5295`. Pendiente: definir el hosting de producción.

## Servicios: `Medidor` como entidad propia (reemplaza el diseño de servicios-en-contrato)
- **Decisión:** un `Medidor` pertenece a un `Inmueble` (CASCADE) y tiene `TipoServicio` (`Agua`/`Electricidad`/`Gas`/`Otro`), `ModoMedidor` (`PorLectura`/`PorPlanilla`) y `Tarifa`. Cada `Inquilino` se vincula a un medidor vía `MedidorInquilino` (con lecturas y `MetodoCobroInquilino`: `Tarifa` = consumo×tarifa, `Prorrateo` = reparte la `FacturaMedidor` (planilla real del periodo) entre los vínculos en prorrateo según su consumo, `Manual` = monto fijo). El cobro de cada inquilino se calcula en `MedidorService.CalcularCobros` y se persiste como `DetalleServicioPago` al crear el `Pago`. Plan original: `C:\Users\msalg\.claude\plans\dreamy-mixing-pond.md`; rediseño en el commit `c886e38` (2026-06-29, rama `feature/medidores-rediseno`).
- **Por qué:** el caso real del usuario tiene medidores compartidos por varios inquilinos (agua de un edificio) y medidores individuales (luz por unidad) — modelar el medidor como entidad propia con inquilinos vinculados soporta ambos casos y el prorrateo entre N inquilinos, algo que el diseño anterior (servicio fijo en el contrato + planilla por inmueble completo) no representaba bien cuando un mismo medidor servía a varios contratos.
- **Descartado:** el diseño anterior de **`ServicioContrato`** (servicio incluido en el contrato, con `ModalidadServicio` `MontoFijo`/`PorConsumo`) + **`CostoServicio`** (planilla por inmueble+tipo+mes/año) — implementado el 2026-06-28 y **dropeado** un día después en la migración `MedidoresRediseno` porque no permitía prorratear una misma planilla entre varios inquilinos vinculados a un medidor compartido, solo asumía pérdida a nivel de todo el inmueble. **Gas** como tipo de servicio activo — sigue en el enum `TipoServicio` pero no se usa en la práctica (bombona personal en Ecuador, no es servicio del arrendador).
- **Estado:** vigente. Migración `MedidoresRediseno` aplicada (dropea `ServiciosContrato`/`CostosServicio`, crea `Medidores`/`MedidoresInquilino`/`FacturasMedidor`/`NotificacionesPendientes`). 59/59 tests en `MedidorServiceTests.cs` (tarifa, manual, prorrateo, pérdida). `Pago.Servicios` se mantiene como suma (compat recibo/Ingresos); el desglose por tipo vive en `DetalleServicioPago`, sin cambios respecto al diseño anterior.

## Tiempo real con SignalR (Pago/Contrato) — evento genérico, best-effort
- **Decisión (2026-07-07, rama `feature/signalr-google-oauth`):** SignalR nativo de ASP.NET Core. Hub único `DatosHub` (`/hubs/datos`, `[Authorize]`, sin métodos — los clientes solo escuchan). El JWT viaja por query string `?access_token=` SOLO en paths `/hubs/*` (evento `OnMessageReceived`); las rutas `/api` siguen con Bearer header. `IDataChangeNotifier` emite un único evento `"CambioDatos"(entidad, usuarioId, accion)` a `Clients.All` desde `PagoService`/`ContratoService` al final de Crear/Update/Delete, envuelto en try/catch + `ILogger` (**best-effort**: un fallo de SignalR nunca hace fallar la operación ya persistida). Cliente compartido `SignalRClient` en `RentaFacil.UI` (`WithAutomaticReconnect`, token de `ITokenStore`), Singleton en MAUI / Scoped en Web; hoy solo `Pagos.razor` se suscribe.
- **Por qué:** el usuario quería ver los cambios de un cliente reflejados en el otro sin refrescar manualmente; SignalR viene integrado en ASP.NET Core (sin dependencias externas) y degrada solo (WebSocket → SSE → long polling). Alcance mínimo (Pago/Contrato, un solo consumidor) para validar la mecánica antes de extenderla.
- **Descartado:** **polling por intervalo** (simular tiempo real refrescando cada X segundos) — genera tráfico constante sin cambios y latencia perceptible; SignalR empuja solo cuando hay mutación. **Agrupar por usuario** (`Clients.User(...)`) — innecesario con un solo arrendador; el `usuarioId` ya viaja en el payload, agrupar después es aditivo.
- **Estado:** vigente. Limitaciones conocidas: borrar un Contrato cascada-borra Pagos a nivel BD sin emitir evento `"Pago"`; los eventos `"Contrato"` aún no tienen página suscrita; revisar el agrupamiento por usuario antes del multiusuario real.

## Login con Google OAuth 2.0 — cimientos con validación de ID token en la API
- **Decisión (2026-07-07, rama `feature/signalr-google-oauth`):** el flujo objetivo es que el **cliente** (MAUI/WASM) obtenga el ID token de Google y lo mande a `POST api/auth/login-google`; la API lo valida con **`Google.Apis.Auth`** (`GoogleJsonWebSignature.ValidateAsync`, con `Audience = Google:ClientId`) detrás de la interfaz mockeable `IValidadorTokenGoogle`, y emite el **JWT propio de siempre**. Matching: `GoogleId` → `Email` (solo si `EmailVerified` — **anti account-takeover**) → auto-registro solo si `Google:PermitirRegistro=true` (default false), con dedupe del `NombreUsuario` truncado contra el índice único. Modelo: `Usuario.GoogleId` (índice único filtrado) y `PasswordHash` nullable (migración `AgregarGoogleIdUsuario`; guard en `LoginAsync` con `IsNullOrEmpty` antes de `BCrypt.Verify`). Sin `Google:ClientId` la API arranca normal y el endpoint devuelve 503. UI: abstracción `IProveedorGoogle` con `ProveedorGoogleNoSoportado` en ambos hosts → botón "Continuar con Google" oculto hasta que exista impl real.
- **Por qué:** deja todo listo para activar Google login sin re-arquitectura: solo falta crear credenciales en Google Cloud Console (user-secrets `Google:ClientId`) e implementar `IProveedorGoogle` por plataforma. La API nunca maneja el flujo de navegador (eso es del cliente), y la validación queda mockeable para tests (12 casos cubren el matching completo).
- **Descartado:** **middleware JwtBearer/OpenIdConnect para validar el token de Google** — el token llega en el body (no en el header del esquema propio) y exigiría un segundo esquema o cablear `ConfigurationManager<OpenIdConnectConfiguration>` a mano sin beneficio frente a la librería oficial (que cachea los JWKS de Google y valida firma/issuer/exp/aud en una llamada). **Vincular por email sin `email_verified`** — detectado en revisión como vector de account-takeover, corregido antes del merge.
- **Estado:** cimientos vigentes e **inactivos** (sin credenciales). Nota: el `Down()` de la migración deja `PasswordHash=""` en rollback manual (solo operación dev; el guard `IsNullOrEmpty` lo cubre).

## `InvariantCulture` en la API + `MoneyFormatter` es-EC + infraestructura `.resx`
- **Decisión:** la API y MAUI fuerzan `CultureInfo.DefaultThreadCurrentCulture` al arrancar (`InvariantCulture` en la API, `es-EC` en MAUI). Todo formateo de dinero para mostrar al usuario (vistas MAUI + recibos PDF) pasa por `MoneyFormatter.Mostrar()` (`RentaFacil.Shared/Globalization/MoneyFormatter.cs`), nunca `.ToString()`/`"F2"` directo. Se agregó infraestructura `.resx` (`SharedResources.es.resx`/`.en.resx`) para multiidioma futuro, aunque hoy solo español está poblado. Plan: `docs/superpowers/plans/2026-06-26-globalizacion.md`.
- **Por qué:** los inputs de monto en MAUI (`type="number"`/`InputNumber`) ya eran seguros por diseño de Blazor (parsean en formato invariante sin importar la cultura del dispositivo), pero la *visualización* (`$@valor`, `.ToString("F2")`) sí dependía de la `CurrentCulture` del hilo — un riesgo real si el servidor de producción corre con un locale distinto al de desarrollo, o si el recibo PDF se genera en un hilo con cultura distinta.
- **Descartado:** migrar los inputs de monto a `type="text"` con parseo manual (lo sugería el borrador inicial del plan) — habría sido una regresión, no una mejora, porque los inputs ya eran culture-safe.
- **Estado:** vigente. Verificado: 50 tests en verde (incluye `MoneyFormatterTests`), recibo PDF real muestra `$500,00` (coma decimal es-EC), build de API y MAUI Android limpios.

## CORS abierto y HTTPS redirection deshabilitado en la API
- **Decisión:** `Program.cs` registra una política CORS `AllowAnyOrigin/AllowAnyMethod/AllowAnyHeader` y comenta explícitamente `app.UseHttpsRedirection()` con la nota "Comentado para permitir conexiones HTTP desde el celular en LAN".
- **Por qué:** permitir que el cliente MAUI en un celular real (sin certificado TLS de confianza) se conecte a la API corriendo en la misma LAN.
- **Descartado:** exigir HTTPS con certificado autofirmado o configurar `mkcert`/similar — no hay evidencia de que se haya intentado.
- **Estado:** vigente mientras todo corra en LAN. **Revisar antes de exponer la API a internet** (Fase 2 — Render, ver fases de despliegue en `flujo-de-trabajo.md`); no es aceptable en producción.
